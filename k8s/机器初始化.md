# KubeKey 部署前：多服务器初始化与 SSH 免密配置手册

> **适用环境**：Ubuntu Server 24.04 LTS、物理机/虚拟机、KubeKey 4.x、Kubernetes 3 Control Plane + 2 Worker。  
> **版本**：v1.0 · **编写日期**：2026-11-03  
> **范围**：静态 IP、网关/DNS、主机名、主机解析、运维账户、SSH 公钥登录、批量验证、KubeKey Inventory 对接。  
> **不包含**：Kubernetes 的完整安装、etcd/存储/CNI 配置、API VIP 实际部署；这些需要结合 KubeKey 集群配置单独完成。

## 0. 最重要的注意事项

1. **以下 IP、接口名、网关、DNS、用户名均为示例。执行前逐台替换并核实，不要照抄到现网。**
2. **远程修改静态 IP 可能立即断开 SSH。** 必须具备 IPMI/iDRAC/iLO/KVM 或虚拟机控制台；先改一台、验证一台，再处理下一台。`netplan try` 可提供超时回退，但不保证在所有复杂网络场景中可靠回退。
3. **不要在所有服务器同时执行网络切换。** SSH 的批量化只用于网络已经稳定之后。
4. **不要将 SSH 私钥、密码、含密钥内容的文件提交 GitLab。** `inventory.yaml` 中仅引用管理机上的密钥文件路径。
5. **SSH 免密是“公钥认证”，不是取消身份认证。** 在确认密钥登录和 sudo 正常之前，不得禁用密码登录。
6. **API 虚拟 IP 不是服务器静态 IP。** 本文预留的 VIP 必须由后续 kube-vip 或独立 LB 提供，不能直接绑定到多台服务器的普通网卡。

## 1. 部署拓扑及地址规划

本例使用单网段 `192.168.50.0/24`，默认网关 `192.168.50.1`，DNS 示例为 `192.168.50.1`（假设网关同时提供 DNS）。实际生产应优先使用企业内部 DNS/NTP。

| 角色 | 主机名 | 示例管理 IP | 用途 |
|---|---|---|---|
| 运维/部署机（推荐独立） | `k8s-admin` | `192.168.50.10` | 运行 KubeKey、保存密钥和配置 |
| Master 1 | `k8s-cp01` | `192.168.50.11` | Kubernetes Control Plane |
| Master 2 | `k8s-cp02` | `192.168.50.12` | Kubernetes Control Plane |
| Master 3 | `k8s-cp03` | `192.168.50.13` | Kubernetes Control Plane |
| Worker 1 | `k8s-worker01` | `192.168.50.21` | 应用负载 |
| Worker 2 | `k8s-worker02` | `192.168.50.22` | 应用负载 |
| API VIP（预留） | `k8s-api` | `192.168.50.100` | 未来 kube-vip/负载均衡入口，本文不负责创建 |

网络参数：

```text
子网 CIDR          192.168.50.0/24
子网掩码           255.255.255.0
网关               192.168.50.1
首选 DNS           192.168.50.1        # 必须实际提供 DNS 服务
备用 DNS           1.1.1.1             # 仅公网可访问时使用；纯内网请替换
管理 SSH 端口      22/tcp
节点互连           使用管理/内网 IP
Pod CIDR           后续在 KubeKey 中另行规划，不能与已有网段重叠
Service CIDR       后续在 KubeKey 中另行规划，不能与已有网段重叠
```

**关键判断**：独立 `k8s-admin` 可用一台小型运维机、虚拟机或堡垒机承担；它不一定是第六个 K8s 节点。如果没有独立管理机，可以先在 `k8s-cp01` 上执行 KubeKey，但需要妥善备份配置与部署密钥。

## 2. 所有机器：确认操作系统与当前网络

使用当前可用账户逐台登录（此时不要批量改 IP）：

```bash
cat /etc/os-release
uname -m
hostnamectl
ip -br link
ip -4 -br addr
ip -4 route
ip route get 1.1.1.1         # 离线环境可换为真实网关或运维机地址
resolvectl status
ls -la /etc/netplan/
sudo netplan get
```

记录**实际网卡名称**（如 `ens18`、`eno1`、`enp3s0`）、MAC 地址、现有 IP、网关、DNS、连接交换机端口及 VLAN。本文示例使用 `eno1`，**不要假定所有服务器的网卡都叫 `eno1`**。

如果机器有多个网卡、网桥、Bond、VLAN、LACP 或 SAN 存储网络，应先按现网设计调整 Netplan；不要直接使用下方的单网卡模板。

## 3. 所有机器：配置静态 IPv4 地址（Netplan）

### 3.1 先备份网络配置

以下操作在**每台服务器本地控制台**或有可靠带外管理的 SSH 会话中执行：

```bash
sudo mkdir -p /root/network-backups
BACKUP_DIR="/root/network-backups/netplan-$(date +%Y%m%d-%H%M%S)"
sudo mkdir -p "$BACKUP_DIR"
sudo cp -a /etc/netplan/. "$BACKUP_DIR/"
printf '备份位置: %s\n' "$BACKUP_DIR"

# 查看所有 Netplan 配置文件，检查是否由 cloud-init 管理
sudo ls -l /etc/netplan/
sudo grep -R -nE 'dhcp4|addresses|routes|renderer' /etc/netplan/ || true
```

**重要**：Netplan 会合并多个 YAML。若旧文件仍为相同网卡启用 DHCP 或定义默认路由，可能与新静态配置冲突。必须在确认网卡后，**只保留该接口的一套生效配置**；不要无脑覆盖全部网络文件。

### 3.2 如果网络由 cloud-init 生成

若 `/etc/netplan/50-cloud-init.yaml` 等文件明确标注由 cloud-init 生成，且以后希望由本地 Netplan 持久管理网络，可在**经控制台确认**后执行：

```bash
sudo install -d -m 755 /etc/cloud/cloud.cfg.d
printf 'network: {config: disabled}\n' | \
  sudo tee /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
```

此操作仅关闭 cloud-init 的网络配置生成能力，**不是禁用整个 cloud-init 服务**。如服务器依赖云平台动态注入网络设置，需优先使用云平台原生配置方式。

### 3.3 创建静态网络文件——以 `k8s-cp01` 为例

以下示例假设 `k8s-cp01` 使用网卡 `eno1`、IP `192.168.50.11/24`。先在本地编辑暂存文件：

```bash
cat > /tmp/01-k8s-static.yaml <<'YAML'
network:
  version: 2
  renderer: networkd
  ethernets:
    eno1:                        # 换成实际网卡名
      dhcp4: false
      dhcp6: false
      addresses:
        - 192.168.50.11/24      # 换成此服务器对应的 IP
      routes:
        - to: default
          via: 192.168.50.1    # 换成实际网关
      nameservers:
        addresses:
          - 192.168.50.1       # 必须是可用 DNS
          - 1.1.1.1            # 纯内网部署应替换为内网 DNS
YAML

cat /tmp/01-k8s-static.yaml
```

核对无误后，将原来**管理此网卡**的 `/etc/netplan/*.yaml` 配置从活动目录移到备份目录（不影响其他网卡的必要配置），再安装新文件：

```bash
# 【示例】仅当 /etc/netplan/50-cloud-init.yaml 是该网卡旧配置时才执行：
sudo mv /etc/netplan/50-cloud-init.yaml "$BACKUP_DIR/50-cloud-init.yaml.old"

# 将新文件设为只有 root 能读写
sudo install -m 600 /tmp/01-k8s-static.yaml /etc/netplan/01-k8s-static.yaml

# 仅生成/校验配置，不立即切网
sudo netplan generate
sudo netplan get
```

> 若 Ubuntu 当前使用 NetworkManager（例如桌面环境），或存在其他网络配置文件，应选择相应 renderer 并按实际配置迁移，不能直接套用 `networkd`。

### 3.4 先尝试切换，再确认

```bash
# 必须在可交互终端中执行，180 秒内确认，否则尝试回滚
sudo netplan try --timeout 180
```

接着在**新开终端**测试新 IP 可登录：

```bash
ssh <原有用户>@192.168.50.11
```

同时从服务器控制台检查：

```bash
ip -4 -br addr
ip -4 route
ip route get 192.168.50.1
ping -c 3 192.168.50.1
resolvectl status
getent hosts ubuntu.com           # 在线环境检测 DNS；纯内网使用内部域名
```

确认网络正常后，在 `netplan try` 的原终端按提示确认；若回退或异常，使用**带外控制台**和备份文件修复。特殊网桥/VLAN 配置的回滚可能不完美，不要仅依赖自动回滚。**切换成功前，禁止关闭原控制台。**

### 3.5 其他节点需要替换的值

| 服务器 | `addresses` 配置 | 网卡名 |
|---|---|---|
| `k8s-cp01` | `192.168.50.11/24` | 填实际网卡 |
| `k8s-cp02` | `192.168.50.12/24` | 填实际网卡 |
| `k8s-cp03` | `192.168.50.13/24` | 填实际网卡 |
| `k8s-worker01` | `192.168.50.21/24` | 填实际网卡 |
| `k8s-worker02` | `192.168.50.22/24` | 填实际网卡 |
| `k8s-admin`（如有） | `192.168.50.10/24` | 填实际网卡 |

逐台应用并检查 IP 不冲突。若使用静态地址与 DHCP 混合环境，应在 DHCP 服务器排除这些静态地址，防止后续租约冲突。

## 4. 所有机器：设置持久主机名

在各台机器执行对应命令（**每台只执行自己的那条**）：

```bash
# Master 01
sudo hostnamectl set-hostname k8s-cp01

# Master 02
sudo hostnamectl set-hostname k8s-cp02

# Master 03
sudo hostnamectl set-hostname k8s-cp03

# Worker 01
sudo hostnamectl set-hostname k8s-worker01

# Worker 02
sudo hostnamectl set-hostname k8s-worker02

# 管理机（如果存在）
sudo hostnamectl set-hostname k8s-admin
```

建议使用小写英文字母、数字和连字符；避免下划线和不稳定的动态命名。验证：

```bash
hostname
hostnamectl --static
cat /etc/hostname
```

### 4.1 `/etc/hosts` 固定映射

以下各节点都添加**相同的公共映射段**，并保留各自原有 `localhost` / IPv6 必需项：

```text
# BEGIN K8S HOSTS
192.168.50.10  k8s-admin
192.168.50.11  k8s-cp01
192.168.50.12  k8s-cp02
192.168.50.13  k8s-cp03
192.168.50.21  k8s-worker01
192.168.50.22  k8s-worker02
192.168.50.100 k8s-api
# END K8S HOSTS
```

如果不用独立管理机，删除 `k8s-admin` 这一行。`k8s-api` 此时只能解析到预留 IP，**不能代表 API VIP 已能访问**。

可以编辑：

```bash
sudo cp /etc/hosts "/etc/hosts.bak.$(date +%Y%m%d-%H%M%S)"
sudoedit /etc/hosts
```

如 `/etc/hosts` 中存在 `127.0.1.1 <旧主机名>`，应将旧主机名修改为**本机**新主机名，例如在 `k8s-cp01` 上：

```text
127.0.0.1 localhost
127.0.1.1 k8s-cp01
```

不要将别的节点名指向 `127.0.1.1`。建议生产集群后续通过内部 DNS 统一管理解析，`/etc/hosts` 可作为小集群初始化方案。

校验：

```bash
getent hosts k8s-cp01
getent hosts k8s-cp02
getent hosts k8s-cp03
getent hosts k8s-worker01
getent hosts k8s-worker02
```

## 5. SSH 免密架构及前置准备

本文采用**中心化单向免密**：

```text
k8s-admin (KubeKey / SSH 私钥)
    |
    +---- SSH 22/tcp --> k8s-cp01
    +---- SSH 22/tcp --> k8s-cp02
    +---- SSH 22/tcp --> k8s-cp03
    +---- SSH 22/tcp --> k8s-worker01
    +---- SSH 22/tcp --> k8s-worker02
```

不要求所有节点两两互相免密，这样更容易回收权限、降低私钥扩散风险。

在全部节点及运维机检查/安装 SSH：

```bash
sudo apt-get update
sudo apt-get install -y openssh-server openssh-client sudo curl tar openssl
sudo systemctl enable --now ssh
sudo systemctl status ssh --no-pager
```

## 6. 所有工作节点：创建 KubeKey 专用运维账户

> **安全选择**：建议使用专用账户 `kkadmin`、SSH 公钥认证、受控 sudo。由于安装软件和系统配置需要管理员权限，本文为专用部署节点提供 `NOPASSWD:ALL` 示例；这是高权限授权，必须限制来源主机和保管私钥，并由公司安全策略批准。

在 `k8s-cp01/02/03`、`k8s-worker01/02` 上，使用**已有** sudo 管理员账户执行：

```bash
# 首次创建时会提示设置 kkadmin 密码，供首次分发公钥使用
sudo adduser kkadmin
sudo usermod -aG sudo kkadmin

# KubeKey 执行系统级配置需要非交互 sudo
printf 'kkadmin ALL=(ALL) NOPASSWD:ALL\n' | \
  sudo tee /etc/sudoers.d/90-kkadmin
sudo chmod 440 /etc/sudoers.d/90-kkadmin
sudo visudo -cf /etc/sudoers.d/90-kkadmin
id kkadmin
```

如果管理机 `k8s-admin` 也运行 KubeKey，可以在管理机创建同名账号，但不一定需要赋予管理机的 `NOPASSWD:ALL` 权限。**切勿以多人共享账户进行日常办公**，`kkadmin` 限用于集群部署/维护。

## 7. 管理机：生成专用 SSH 密钥

在管理机使用 `kkadmin` 登录后执行：

```bash
sudo -iu kkadmin

install -d -m 700 ~/.ssh
ssh-keygen -t ed25519 \
  -f ~/.ssh/id_ed25519_kubekey \
  -C "kkadmin@k8s-admin-kubekey"

chmod 600 ~/.ssh/id_ed25519_kubekey
chmod 644 ~/.ssh/id_ed25519_kubekey.pub
cat ~/.ssh/id_ed25519_kubekey.pub
```

生产优先采用**带口令私钥 + 受控 ssh-agent**。若当前 KubeKey 执行方式不支持从 agent/带口令文件读取密钥，需要使用受严格访问控制的专用部署机和受保护的自动化凭据；**不要把无口令私钥分发给业务节点**。本文后续命令均通过指定私钥文件登录。

## 8. 管理机：给五台节点分发 SSH 公钥

> 首次执行 `ssh-copy-id` 前必须通过可信渠道核实各机器的 SSH Host Key 指纹。首次出现 `Are you sure you want to continue connecting` 时核对后再确认，**不要使用 `StrictHostKeyChecking=no` 忽略身份校验**。

在管理机 `kkadmin` 用户下执行：

```bash
KEY="$HOME/.ssh/id_ed25519_kubekey"

ssh-copy-id -i "${KEY}.pub" kkadmin@192.168.50.11
ssh-copy-id -i "${KEY}.pub" kkadmin@192.168.50.12
ssh-copy-id -i "${KEY}.pub" kkadmin@192.168.50.13
ssh-copy-id -i "${KEY}.pub" kkadmin@192.168.50.21
ssh-copy-id -i "${KEY}.pub" kkadmin@192.168.50.22
```

每台第一次可能要求输入**该节点** `kkadmin` 用户密码。这一步完成后，再使用 SSH 私钥验证，而不是依赖密码。

### 8.1 可选：一次循环分发（仍需交互输入密码并核实指纹）

```bash
KEY="$HOME/.ssh/id_ed25519_kubekey"
for ip in 192.168.50.11 192.168.50.12 192.168.50.13 192.168.50.21 192.168.50.22; do
  echo "========== $ip ==========" 
  ssh-copy-id -i "${KEY}.pub" "kkadmin@${ip}" || {
    echo "FAIL: $ip" >&2
    exit 1
  }
done
```

**安全提醒**：`ssh-keyscan` 可用于采集公钥但不能自行证明目标身份。生产环境应比对控制台看到的 SSH Host Key 指纹或可信 CMDB 记录。

## 9. 管理机：SSH 客户端配置与免密测试

将 SSH 配置加入管理机的 `/home/kkadmin/.ssh/config`：

```sshconfig
Host k8s-cp01
    HostName 192.168.50.11
Host k8s-cp02
    HostName 192.168.50.12
Host k8s-cp03
    HostName 192.168.50.13
Host k8s-worker01
    HostName 192.168.50.21
Host k8s-worker02
    HostName 192.168.50.22

Host k8s-cp01 k8s-cp02 k8s-cp03 k8s-worker01 k8s-worker02
    User kkadmin
    Port 22
    IdentityFile ~/.ssh/id_ed25519_kubekey
    IdentitiesOnly yes
    ServerAliveInterval 30
```

```bash
chmod 600 ~/.ssh/config
ssh k8s-cp01 'hostname; whoami'
ssh k8s-worker01 'hostname; whoami'
```

使用 `BatchMode=yes` 可以检查是否不需要交互密码。如果采用了**私钥口令**，请先通过 ssh-agent 解锁私钥：

```bash
# 如果密钥带口令：先在当前会话添加密钥
ssh-add ~/.ssh/id_ed25519_kubekey

for host in k8s-cp01 k8s-cp02 k8s-cp03 k8s-worker01 k8s-worker02; do
  echo "==== ${host} ===="
  ssh -o BatchMode=yes -o ConnectTimeout=6 "$host" \
    'printf "hostname=%s ip=%s user=%s\n" "$(hostname)" "$(hostname -I | awk '\''{print $1}'\'')" "$(whoami)"; sudo -n true' \
    && echo 'PASS: SSH + sudo' \
    || echo 'FAIL: check SSH/key/sudo'
done
```

如失败检查：

```bash
# 管理机
ssh -vvv -i ~/.ssh/id_ed25519_kubekey kkadmin@192.168.50.11

# 目标节点控制台
sudo journalctl -u ssh -n 100 --no-pager
sudo ls -ld /home/kkadmin /home/kkadmin/.ssh
sudo ls -l /home/kkadmin/.ssh/authorized_keys
```

目标节点推荐权限：目录 `~/.ssh` 为 `700`，`authorized_keys` 为 `600`，且归属 `kkadmin`：

```bash
sudo chown -R kkadmin:kkadmin /home/kkadmin/.ssh
sudo chmod 700 /home/kkadmin/.ssh
sudo chmod 600 /home/kkadmin/.ssh/authorized_keys
```

## 10. 已验证免密后：加强 SSH 安全配置（可选但推荐）

**必须先保持至少一个已成功验证的 SSH 公钥会话，并确保带外控制台可用。** 在每个节点执行：

```bash
sudo tee /etc/ssh/sshd_config.d/60-k8s-hardening.conf >/dev/null <<'EOF_SSH'
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
EOF_SSH

sudo sshd -t
sudo systemctl reload ssh

# 查看最终生效值，注意更早的配置片段可能覆盖后面的片段
sudo sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '
```

再开新终端进行 `ssh -o BatchMode=yes ...` 测试，确认可用后才关闭旧连接。由于 Ubuntu 支持 `/etc/ssh/sshd_config.d/*.conf`，**配置优先级需以 `sshd -T` 实测为准**。若有堡垒机/集中身份管理，按公司安全策略调整而不是机械关闭所有密码途径。

## 11. 管理机：批量核查主机名、IP、SSH、sudo、时间

在管理机的 `kkadmin` 家目录创建：

```bash
cat > ~/check-k8s-nodes.sh <<'BASH'
#!/usr/bin/env bash
set -uo pipefail

HOSTS=(k8s-cp01 k8s-cp02 k8s-cp03 k8s-worker01 k8s-worker02)
FAIL=0
for host in "${HOSTS[@]}"; do
  echo "========== ${host} =========="
  if ! ssh -o BatchMode=yes -o ConnectTimeout=8 "$host" 'bash -s' <<'REMOTE'
set -euo pipefail
printf 'hostname: '; hostname
printf 'IPv4: '; hostname -I
printf 'gateway: '; ip -4 route show default
printf 'DNS: '; resolvectl dns | head -n 4
printf 'sudo noninteractive: '; sudo -n true && echo OK
printf 'time synchronization: '; timedatectl show -p NTPSynchronized
printf 'node mapping: '; getent hosts k8s-cp01 | head -n 1
REMOTE
  then
    echo "FAILED: ${host}" >&2
    FAIL=1
  fi
  echo
done
exit "$FAIL"
BASH
chmod +x ~/check-k8s-nodes.sh
~/check-k8s-nodes.sh
```

> `NTPSynchronized=yes` 取决于时间同步服务和可访问的 NTP 源；物理机应保证 chrony/systemd-timesyncd 使用统一可靠的内部 NTP，不建议节点自行相互校时。

### 11.1 一次性汇总 TCP 22 可达性（管理机）

```bash
for ip in 192.168.50.11 192.168.50.12 192.168.50.13 192.168.50.21 192.168.50.22; do
  if timeout 3 bash -c "</dev/tcp/${ip}/22" 2>/dev/null; then
    echo "${ip}:22 OK"
  else
    echo "${ip}:22 FAIL"
  fi
done
```

本命令只说明 TCP 端口是否可连通，不代表 SSH 认证成功。

**关于 etcd**：KubeKey 4.x 的 Inventory 文档指出 `etcd` 组与外置 etcd 部署方式有关；若采用 stacked etcd 或其他模式，应先依据 `config.yaml` 的实际部署模式确定角色，不能机械复制示例的 `etcd` 分组。`inventory.yaml` 引用的是**管理机本地的**私钥绝对路径，不需要、也不应将私钥复制到节点。

```bash

./kk create cluster -i inventory.yaml -c config.yaml
```

## 13. 批量执行主机命名与 hosts 更新的可选脚本

**前提**：五台机器 IP 已各自配置并稳定、SSH 免密已经成功、管理员 sudo 已验证。此脚本只改主机名和主机解析，不改 IP，不自动修改 SSH 密码策略。

在管理机 `kkadmin` 用户下创建：

```bash
cat > ~/batch-hostname-hosts.sh <<'BASH'
#!/usr/bin/env bash
set -euo pipefail

# 本次部署的 IP 与主机名（必须先核对）
ROWS=(
  '192.168.50.11 k8s-cp01'
  '192.168.50.12 k8s-cp02'
  '192.168.50.13 k8s-cp03'
  '192.168.50.21 k8s-worker01'
  '192.168.50.22 k8s-worker02'
)

# 在 hosts 中创建有边界的可管理片段；不触碰原有 localhost 解析
BLOCK=$(cat <<'HOSTS'
# BEGIN K8S HOSTS
192.168.50.10  k8s-admin
192.168.50.11  k8s-cp01
192.168.50.12  k8s-cp02
192.168.50.13  k8s-cp03
192.168.50.21  k8s-worker01
192.168.50.22  k8s-worker02
192.168.50.100 k8s-api
# END K8S HOSTS
HOSTS
)

for row in "${ROWS[@]}"; do
  read -r ip name <<< "$row"
  echo "== Updating $name ($ip) =="
  ssh -o BatchMode=yes "kkadmin@$ip" \
    "sudo hostnamectl set-hostname '$name'; sudo cp /etc/hosts /etc/hosts.bak.\$(date +%Y%m%d-%H%M%S); sudo sed -i '/^# BEGIN K8S HOSTS$/,/^# END K8S HOSTS$/d' /etc/hosts"

  printf '%s\n' "$BLOCK" | ssh -o BatchMode=yes "kkadmin@$ip" \
    'sudo tee -a /etc/hosts >/dev/null'

  # 修正本机 127.0.1.1 映射（如存在）
  ssh -o BatchMode=yes "kkadmin@$ip" \
    "if grep -qE '^127\\.0\\.1\\.1([[:space:]]|$)' /etc/hosts; then sudo sed -i -E 's/^127\\.0\\.1\\.1.*/127.0.1.1 $name/' /etc/hosts; fi; hostname; getent hosts '$name'"
done
BASH
chmod +x ~/batch-hostname-hosts.sh

# 审查脚本后再运行！
less ~/batch-hostname-hosts.sh
~/batch-hostname-hosts.sh
```

**注意**：脚本采用追加标记块的方式管理 `/etc/hosts`。若文件原有对应主机名的其他 IP 映射（不在标记块内），必须先人工清理冲突，避免同名解析歧义。如果全网已经有正确 DNS，优先使用 DNS 而不是这个脚本。

## 14. 常见问题与排障

| 问题 | 排查顺序 |
|---|---|
| `SSH Connection refused` | `ss -lntp | grep :22`、`systemctl status ssh`、安全组/防火墙 |
| `Permission denied (publickey)` | 用户名、密钥文件、`authorized_keys`、权限、`ssh -vvv`、`journalctl -u ssh` |
| SSH 可以登录但 KubeKey 报 sudo 错 | `sudo -n true`、`id kkadmin`、`visudo -cf`、实际 sudo 策略 |
| 静态 IP 改完失联 | 带外控制台检查网卡名、掩码、VLAN、网关、Netplan 文件冲突；恢复备份 |
| IP 能 ping，主机名不能解析 | `getent hosts`、`/etc/hosts` 重复条目、`resolvectl status` |
| DNS 正常但节点之间断连 | 交换机 VLAN、ACL、主机防火墙、路由、MTU |
| `netplan generate` 失败 | YAML 缩进、错误的网卡名称、文件权限、冲突的网络配置 |
| `Host key verification failed` | 核实主机重装/变更、比对 SSH Host Key 指纹后再更新 `known_hosts` |
| SSH 很慢 | DNS 反向解析、网络时延、SSH GSSAPI、主机资源，结合日志排查 |
| 无法访问 API VIP | 目前仅预留了地址；需实际部署并验证 kube-vip 或 LB |

### 14.1 SSH Host Key 发生变化时

不要通过关闭主机身份校验来绕过警告。先在目标节点控制台确认：

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

与运维管理机收到的指纹比较，确认确实发生合法重装或换机之后再更新 `known_hosts`：

```bash
ssh-keygen -R 192.168.50.11
ssh -i ~/.ssh/id_ed25519_kubekey kkadmin@192.168.50.11
```

## 15. 防火墙与安全边界（初始化阶段）

- SSH `22/tcp`：优先只允许 `k8s-admin`/堡垒机所在管理网段访问，不对公网开放。
- Kubernetes 后续会使用 API `6443/tcp`、etcd `2379-2380/tcp`、kubelet `10250/tcp`、CNI（可能包括 BGP/IPIP/VXLAN）等端口；**具体取决于安装架构和网络插件**，按 KubeKey 官方端口表逐项核对。
- 不建议为了“方便部署”长期完全关闭主机防火墙；设计明确的节点互信网段和所需端口。
- 不建议将存储、etcd、API、SSH 暴露在公网地址；优先使用受控内网。
- 记录所有变更时间、变更人、控制台访问方式和回滚方案。
